# Scouty UX 라이팅 가이드

## 1. 보이스

Scouty는 좋은 작업을 발견하는 설렘과 처음 연락하는 순간의 부담을 함께 이해한다. 과장해서 들뜨게 만들거나 딱딱하게 심사하지 않고, 사용자가 다음 행동을 정확히 판단하도록 돕는다.

보이스는 다음 다섯 기준을 유지한다.

| 기준 | 의미 | 점검 질문 |
|---|---|---|
| 명확한 | 익숙한 단어로 사실을 정확히 전달한다. | 한 번 읽고 이해할 수 있는가? |
| 간결한 | 지금 필요한 정보만 필요한 만큼 말한다. | 지워도 의미가 같은 말이 있는가? |
| 친근한 | 자연스러운 해요체를 사용한다. | 실제 대화에서 쓸 수 있는 말인가? |
| 존중하는 | 선택을 압박하거나 비용을 숨기지 않는다. | 사용자가 거절·취소해도 존중받는가? |
| 공감하는 | 사용자의 상황과 감정을 인정한다. | 문제를 사용자 탓으로 돌리지 않는가? |

## 2. 기본 문장 규칙

- 본문과 안내는 해요체를 기본으로 한다.
- 제목은 마침표 없이 짧게 쓰고, 본문은 완결된 문장으로 쓴다.
- 한 문장에는 한 가지 정보만 담는다.
- 능동형과 구체적인 동사를 사용한다.
- `~할 수 있습니다`보다 상황에 맞으면 `~할 수 있어요`를 쓴다.
- 버튼에는 행동 결과가 드러나는 동사를 쓴다: `제안 보내기`, `프로젝트 게시하기`.
- 완료 메시지는 완료된 결과를 쓴다: `프로젝트를 저장했어요`.
- 동일한 대상을 화면마다 다른 이름으로 부르지 않는다.
- 느낌표, 이모지, 영어 약어는 꼭 필요한 경우에만 사용한다.

## 3. Scouty 용어

| 사용 | 피하기 | 이유 |
|---|---|---|
| 발견 | 추천 인재 | 사람을 상품이나 순위처럼 보이지 않게 한다. |
| 스카우트 제안 | 지원, 매칭 신청, 섭외 DM | Scouty의 관계 시작 방식을 구분한다. |
| 필요한 역할 | 채용 포지션 | 채용 서비스로 오해하지 않게 한다. |
| 프로젝트 | 스펙, 실적 | 결과물 자체에 집중한다. |
| 다음 프로젝트 | 싫어요, 패스 | 넘기기에 평가 의미를 부여하지 않는다. |
| 수락 | 합격 | 사람을 심사하는 의미를 피한다. |
| 이번 제안은 이어지지 않았어요 | 탈락, 거절당했어요 | 상대를 비난하거나 실패감을 주지 않는다. |
| 보관 | 삭제 | 공개 노출만 멈추고 복구 가능함을 알린다. |
| 매너 온도 | 평점, 신뢰 점수 | 실력·가치 순위가 아님을 분명히 한다. |

개발 코드와 분석 이벤트의 내부 명칭이 다르더라도 사용자 화면에서는 이 용어를 유지한다.

## 4. 정보 순서

안내 문구는 보통 다음 순서로 쓴다.

1. 사용자가 얻는 가치 또는 현재 결과
2. 꼭 알아야 할 조건이나 영향
3. 사용자가 할 수 있는 다음 행동

예시:

> 프로젝트를 게시하면 작업을 본 사람이 스카우트 제안을 보낼 수 있어요. PDF를 올린 뒤 제목, 역할, 해시태그만 입력해 주세요.

권한이나 비용을 먼저 나열하기보다 왜 필요한지 설명한다. 단, 개인정보·되돌릴 수 없는 행동·금전처럼 중요한 영향은 CTA 전에 숨김없이 알린다.

## 5. 상태별 문구

### 로딩과 처리 중

- 기다리는 대상과 완료 후 결과를 함께 말한다.
- 정확히 알 수 없는 완료 시간을 약속하지 않는다.
- 화면을 나가도 되는지 알려준다.

```text
PDF를 프로젝트로 바꾸고 있어요
화면을 나가도 프로필에서 처리 상태를 확인할 수 있어요.
```

### 빈 상태

- 비어 있는 이유를 실패처럼 표현하지 않는다.
- 가능한 다음 행동은 하나만 우선한다.

```text
이 역할의 프로젝트가 아직 없어요
다른 역할을 둘러보거나 나중에 다시 확인해 주세요.
```

### 완료

- `완료되었습니다`보다 무엇이 완료됐는지 쓴다.

```text
스카우트 제안을 보냈어요
상대가 수락하면 채팅을 시작할 수 있어요.
```

### 오류

오류 메시지는 세 가지를 답한다.

1. 무슨 일이 일어났는가?
2. 사용자가 한 작업이나 데이터는 어떻게 되었는가?
3. 지금 무엇을 할 수 있는가?

```text
영상을 처리하지 못했어요
PDF와 입력한 내용은 그대로 남아 있어요. 영상 없이 게시하거나 다시 시도할 수 있어요.
```

- 알 수 없는 원인을 추측하지 않는다.
- 내부 오류 코드, 스택, 공급자 이름을 노출하지 않는다.
- 사용자가 해결할 수 없는 문제에 `다시 확인해 주세요`만 반복하지 않는다.
- 보안상 상세 원인을 말할 수 없더라도 계정 문제인지 일시 오류인지, 사용자가 할 수 있는 범위는 알린다.

## 6. 민감한 순간

### 제안 수락·거절·취소

- 수락 전에는 채팅방 생성과 되돌릴 수 없음을 알려준다.
- 거절 사유를 요구하지 않는다.
- 발신자에게는 결과만 중립적으로 알리고 수신자의 감정을 추측하지 않는다.

| 상태 | 권장 문구 |
|---|---|
| 대기 | 답변을 기다리고 있어요 |
| 수락 | 제안을 수락했어요. 이제 채팅에서 이야기해 보세요. |
| 거절 | 이번 제안은 이어지지 않았어요 |
| 취소 | 보낸 사람이 제안을 취소했어요 |

### 매너 평가

- 질문은 `이번 소통은 어땠나요?` 하나만 사용한다.
- `좋았어요`, `아쉬웠어요`처럼 경험을 묻고 사람 자체를 평가하게 하지 않는다.
- 부정 선택을 경고색으로 과장하지 않는다.

### 통계 표본 부족

- `응답률 0%`처럼 오해를 만드는 숫자를 표시하지 않는다.
- `아직 응답 정보가 부족해요`처럼 판단을 유보할 이유를 설명한다.

## 7. 컴포넌트별 규칙

### Button

- 짧고 구체적인 동작을 쓴다.
- `확인`, `예`, `아니요`만으로 결과가 불명확하면 쓰지 않는다.
- 파괴적 버튼은 대상을 포함한다: `프로젝트 보관하기`, `제안 취소하기`.

### Form

- label은 명사형으로, 도움말은 입력 이유나 형식으로 쓴다.
- placeholder는 예시이며 label을 대신하지 않는다.
- 선택 필드는 `선택`이라고 표시하고 필수 기호를 남발하지 않는다.

### Toast

- 짧은 성공 확인과 되돌리기 가능한 행동에만 사용한다.
- 오류 원인과 해결이 필요한 내용은 toast에만 두지 않는다.

### Notification

- 누가, 무엇을, 어떤 프로젝트를 근거로 행동했는지 필요한 범위에서 알려준다.
- 메시지 본문이나 민감한 제안 내용을 잠금 화면에 그대로 노출하지 않는다.

## 8. 숫자와 시간

- 숫자는 판단에 도움이 될 때만 표시한다.
- 상대 시간과 절대 시간이 혼동될 수 있으면 상세에서 정확한 시각을 제공한다.
- 평균 응답 시간은 PRD의 구간형 문구를 사용한다.
- 온도에는 `°`를 붙이되 실제 체온이나 건강 상태로 오해할 설명을 하지 않는다.
- 제한은 행동 전에 알린다: `PDF · 최대 50MB · 50페이지`.

## 9. 작성 체크리스트

- [ ] 사용자에게 익숙한 단어를 썼다.
- [ ] 한 문장에 한 가지 정보만 있다.
- [ ] 사용자의 잘못을 전제로 하지 않는다.
- [ ] 행동의 결과와 다음 단계를 알 수 있다.
- [ ] 거절·취소·표본 부족을 실패처럼 표현하지 않는다.
- [ ] 버튼만 읽어도 결과를 예상할 수 있다.
- [ ] 스크린 리더가 읽어도 맥락이 유지된다.
- [ ] 개인정보와 자유 텍스트를 불필요하게 반복 노출하지 않는다.
