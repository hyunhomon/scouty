# Scouty 디자인 원칙

## 1. 목적

Scouty의 디자인은 화려한 화면보다 **좋은 작업을 발견하고, 충분히 이해하고, 안전하게 대화를 시작하는 과정**을 선명하게 만드는 데 집중한다.

토스의 단순함, 한 화면에 하나의 핵심, 가치를 먼저 보여주는 방식, 명확하고 존중하는 언어에서 배운다. 다만 금융 서비스의 형태를 복제하지 않고 Scouty의 제품 원칙인 `Project First`, `Proof, Not Profile`, `Connection, Not Management`에 맞게 해석한다.

## 2. 경험 목표

사용자는 Scouty를 다음과 같이 느껴야 한다.

- **보내는 사람:** 좋은 작업자를 발견했고, 왜 제안하는지 분명하게 전달할 수 있다.
- **받는 사람:** 내 작업이 먼저 인정받았고, 부담 없이 제안을 판단할 수 있다.
- **둘 모두:** 무엇이 공개되고 다음에 어떤 일이 일어나는지 예측할 수 있다.

## 3. 핵심 원칙

### 3.1 프로젝트를 주인공으로 둔다

첫인상은 사람의 배경이 아니라 결과물이어야 한다.

- 피드와 스카우트에서 PDF 커버를 가장 큰 시각 요소로 둔다.
- 학교·학년·경력·스펙을 탐색의 앞단에 배치하지 않는다.
- 작성자 정보는 작업의 맥락을 이해하는 데 필요한 수준으로만 보여준다.
- 장식 그래픽이 프로젝트보다 먼저 보이지 않게 한다.

**리뷰 질문:** 작성자 이름과 배경을 가려도 이 화면이 어떤 작업인지 이해할 수 있는가?

### 3.2 한 화면에서는 하나의 판단에 집중한다

화면마다 사용자가 내려야 할 핵심 판단을 하나로 제한한다. 토스의 `One thing per one page`를 Scouty 흐름에 적용한 원칙이다.

- 온보딩에서는 프로필 완성, 스카우트에서는 다음 프로젝트 판단, 제안 상세에서는 수락 여부에 집중한다.
- 같은 위계의 Primary CTA를 두 개 이상 두지 않는다.
- 핵심 판단에 필요하지 않은 정보는 접거나 다음 화면으로 보낸다.
- 한 화면에서 탐색·작성·설정을 동시에 해결하려 하지 않는다.

**리뷰 질문:** 이 화면을 3초 본 사용자가 지금 할 일을 한 문장으로 말할 수 있는가?

### 3.3 가치를 먼저 보여주고 노력을 요청한다

사용자가 입력하거나 결정하기 전에 얻는 가치를 이해하게 한다. 토스의 `Value first, cost later`를 따른다.

- 회원가입 전에 공개 프로젝트를 탐색할 수 있게 한다.
- 포트폴리오 등록을 요구하기 전에 어떤 제안을 보낼 수 있는지 보여준다.
- 권한 요청·업로드·긴 입력 전에 필요한 이유와 결과를 설명한다.
- 제한을 숨기지 않되 가치보다 먼저 경고 목록을 늘어놓지 않는다.

**리뷰 질문:** 사용자는 이 행동을 왜 해야 하는지 비용을 치르기 전에 알 수 있는가?

### 3.4 쉬운 기본값을 주고 선택은 필요할 때 연다

처음부터 모든 옵션을 보여주는 대신 안전한 기본값과 점진적 공개를 사용한다.

- 스카우트 수신 상태의 기본값은 `selective`로 둔다.
- PDF 1페이지를 자동 커버로 사용한다.
- 최근 역할과 사용자 역할을 먼저 제안하되 다른 역할 선택은 막지 않는다.
- 고급 설정은 실제 필요가 생긴 시점에 노출한다.

**리뷰 질문:** 이 선택을 하지 않아도 대부분의 사용자가 안전하게 다음 단계로 갈 수 있는가?

### 3.5 빠르게 발견하되 성급하게 연결하지 않는다

탐색 속도와 관계 형성의 신중함을 분리한다.

- 프로젝트는 빠르게 넘길 수 있게 하고 평가 의미를 붙이지 않는다.
- 제안에는 근거 프로젝트, 역할, 기간, 활동량을 반드시 포함한다.
- 승인 전 자유 DM을 허용하지 않는다.
- 거절·취소는 비난이나 실패처럼 표현하지 않는다.

**리뷰 질문:** 빠른 인터랙션이 사람에 대한 성급한 평가나 원치 않는 연락으로 이어지지 않는가?

### 3.6 상태와 결과를 즉시 설명한다

사용자가 시스템 상태를 추측하게 두지 않는다.

- 업로드, 변환, 전송, 저장, 읽음 상태를 즉시 피드백한다.
- 오류는 발생 사실, 영향, 다음 행동을 함께 알려준다.
- 비동기 작업은 화면을 나가도 다시 확인할 수 있다.
- 실패한 영상 때문에 성공한 PDF까지 잃지 않게 한다.

**리뷰 질문:** 사용자는 방금 한 행동이 성공했는지, 기다려야 하는지, 다시 해야 하는지 아는가?

### 3.7 신뢰를 보여주되 순위를 만들지 않는다

응답 지표와 매너 온도는 연락 가능성을 돕는 맥락이지 사람의 가치나 실력 점수가 아니다.

- 매너 온도와 응답률을 검색 정렬에 사용하지 않는다.
- 표본이 부족하면 숫자 대신 부족한 맥락을 설명한다.
- 긍정·부정 평가 건수와 공개 리뷰를 노출하지 않는다.
- 색, 온도, 숫자 하나만으로 사용자를 좋고 나쁨으로 구분하지 않는다.

**리뷰 질문:** 이 정보가 합리적인 연락 판단을 돕는가, 아니면 사람을 줄 세우는가?

### 3.8 친절함보다 통제권을 먼저 보장한다

친근한 말투가 사용자의 선택권을 대신할 수 없다.

- 취소, 뒤로 가기, 나중에 하기 경로를 숨기지 않는다.
- 삭제·발송·수락처럼 되돌리기 어려운 행동은 결과를 먼저 설명한다.
- 자동 재생, 강제 가입, 위장 CTA, 압박 카운트다운을 사용하지 않는다.
- 스와이프만 가능한 기능을 만들지 않는다.

**리뷰 질문:** 사용자가 불이익이나 혼란 없이 멈추거나 돌아갈 수 있는가?

## 4. 화면 설계 순서

새 화면은 다음 순서로 설계한다.

1. 사용자가 해결하려는 문제를 한 문장으로 쓴다.
2. 화면에서 내려야 할 핵심 판단을 하나 정한다.
3. 그 판단에 꼭 필요한 정보만 남긴다.
4. Primary CTA를 하나 정하고 보조 행동의 위계를 낮춘다.
5. 로딩·빈 상태·오류·완료·권한 없음 상태를 함께 설계한다.
6. 키보드, 스크린 리더, 작은 화면에서도 같은 과업이 가능한지 확인한다.
7. 분석 이벤트가 사용자의 자유 텍스트나 개인정보를 수집하지 않는지 확인한다.

## 5. 디자인 리뷰 체크리스트

- [ ] 프로젝트가 사람의 배경보다 먼저 보인다.
- [ ] 화면의 핵심 판단과 Primary CTA가 각각 하나다.
- [ ] 사용자가 행동의 가치를 먼저 이해한다.
- [ ] 정보가 필요한 시점에 필요한 만큼만 보인다.
- [ ] 상태·오류·다음 행동이 명확하다.
- [ ] 사람을 평가·압박·탈락시키는 표현이 없다.
- [ ] 모든 제스처에 버튼 또는 키보드 대안이 있다.
- [ ] 표본이 부족한 신뢰 지표를 단정적으로 보여주지 않는다.
- [ ] 취소와 뒤로 가기가 예측 가능하다.
