# Scouty 문서 안내

Scouty의 제품·디자인·기술 결정을 한곳에서 찾기 위한 문서 인덱스다. 문서는 대화 기록이 아니라 **현재 유효한 결정**만 남긴다.

## 문서 지도

| 문서 | 답하는 질문 | 주요 독자 |
|---|---|---|
| [PRD](./PRD.md) | 무엇을 왜 만드는가? | 전 구성원 |
| [디자인 원칙](./DESIGN_PRINCIPLES.md) | 어떤 경험을 좋은 경험으로 판단하는가? | Product, Design, Frontend |
| [디자인 시스템](./DESIGN_SYSTEM.md) | 화면을 어떤 시각 언어와 규칙으로 만드는가? | Design, Frontend |
| [UX 라이팅](./UX_WRITING.md) | 사용자에게 어떤 말투와 문장으로 안내하는가? | Product, Design, Frontend |
| [접근성](./ACCESSIBILITY.md) | 누구나 핵심 과업을 수행하게 하려면 무엇을 지켜야 하는가? | Design, Frontend, QA |
| [기술 기준](./TECH_STACK.md) | 어떤 구조와 기술 경계를 사용하는가? | Frontend, Backend, Infra |
| [개발 기준](./DEVELOPMENT_GUIDE.md) | 구현과 검토를 어떤 방식으로 진행하는가? | Engineering, QA |
| [프로덕션 배포](./DEPLOYMENT.md) | 무엇을 준비하고 어떤 순서로 배포·복구하는가? | Engineering, Operations |

구조 변경의 결정 근거는 [`docs/adr`](./adr/)에 기록한다.

## 결정 우선순위

문서 사이에 충돌이 있으면 다음 순서로 판단한다.

1. `PRD.md`의 제품 범위·권한·비즈니스 규칙
2. `DESIGN_PRINCIPLES.md`의 사용자 경험 원칙
3. 분야별 상세 문서의 규격
4. 실제 코드와 설정

실제 코드가 문서와 다르면 코드를 정답으로 간주하지 않는다. 의도된 변경인지 확인한 뒤 문서와 코드를 함께 갱신한다.

## 문서 작성 원칙

- 현재 결정과 검증 가능한 이유를 쓴다.
- 구현 코드에서 바로 확인할 수 있는 세부사항을 장황하게 복제하지 않는다.
- `왜`가 사라지면 같은 논의를 반복할 결정만 기록한다.
- 미정 사항은 확정된 내용처럼 쓰지 않고 소유자와 결정 시점을 남긴다.
- 새 문서는 이 인덱스에 연결한다. 고아 문서를 만들지 않는다.
- 큰 구조 변경은 필요할 때 `docs/adr/`에 ADR로 남긴다.

## 변경 체크리스트

- 제품 동작이 바뀌면 PRD와 인수 조건을 확인한다.
- 화면 원칙이나 토큰이 바뀌면 디자인 원칙과 디자인 시스템을 확인한다.
- 사용자에게 보이는 문구가 바뀌면 UX 라이팅 용어표를 확인한다.
- 새 인터랙션을 추가하면 키보드·스크린 리더·모션 대체 수단을 확인한다.
- 런타임, 데이터 저장소, 외부 서비스가 바뀌면 기술 기준을 갱신한다.
