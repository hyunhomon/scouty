# ADR 0001: 애플리케이션 경계 분리

- 상태: 채택
- 결정일: 2026-08-07

## 배경

초기 MVP 구현에서는 워크스페이스 화면과 Prisma 서비스가 각각 하나의 큰 파일에 모였다. 기능 추가 속도는 빨랐지만, 네트워크 오류 처리·폼 컨트롤·DB 모델 변환이 기능 코드와 섞여 변경 영향 범위를 파악하기 어려워졌다.

## 결정

프런트엔드는 다음 의존 방향을 따른다.

1. `components/ui`: 제품 도메인을 모르는 재사용 가능한 UI 컨트롤
2. `lib/api-client`: HTTP 요청, 재시도, 오류 메시지 정규화
3. `components/workspace`: 온보딩, 프로필/포트폴리오, 스카우트, 채팅/알림 등 기능 단위 화면
4. `ProductWorkspace`: 세션과 전역 읽지 않은 항목 수를 조정하고 기능 화면을 선택하는 얇은 오케스트레이터

백엔드는 Prisma include와 API 응답 매핑을 `core-prisma-mappers.ts`에 격리한다. `PrismaCoreService`는 유스케이스 흐름과 트랜잭션 조정에 집중한다.

## 공통 규칙

- 읽기 요청만 일시적인 네트워크 실패와 408, 429, 5xx 응답을 제한적으로 재시도한다.
- 상태를 바꾸는 요청은 중복 실행을 막기 위해 자동 재시도하지 않는다.
- 텍스트 입력에는 사용자가 기대 형식을 알 수 있는 플레이스홀더를 제공한다.
- 선택 목록은 공통 Radix Select를 사용하며 네이티브 `select`를 직접 추가하지 않는다.
- 파일 입력은 숨겨진 입력을 직접 노출하지 않고 명시적인 액션 버튼으로 연다.
- 기능 모듈은 `components/ui`와 `lib`에 의존할 수 있지만, 공통 계층은 기능 모듈에 의존하지 않는다.

## 결과

기능별 변경 범위와 테스트 위치가 선명해지고, 공통 UX 수정이 한 곳에서 적용된다. 파일 수와 import 수는 늘어나지만 순환 의존을 피하고 오케스트레이터를 작게 유지하는 것을 우선한다.
