# Scouty 접근성 기준

## 1. 목표

Scouty의 공개 탐색부터 포트폴리오 게시, 제안, 채팅까지 핵심 과업은 장애 여부, 입력 방식, 화면 크기와 관계없이 수행할 수 있어야 한다.

MVP 기준은 [WCAG 2.2 Level AA](https://www.w3.org/TR/WCAG22/)다. 자동 검사 통과만으로 완료로 보지 않고 키보드와 스크린 리더 수동 검증을 포함한다.

## 2. 공통 기준

### 키보드와 포커스

- 모든 인터랙션을 키보드만으로 수행할 수 있어야 한다.
- 포커스 순서는 시각적 읽기 순서와 일치해야 한다.
- 포커스 표시를 제거하지 않고 배경과 충분히 대비되게 한다.
- dialog와 sheet는 열린 동안 포커스를 내부에 두고 닫을 때 호출 요소로 되돌린다.
- 스크롤 영역이나 카드 안에 키보드 trap을 만들지 않는다.
- 본문으로 바로 이동하는 skip link를 제공한다.

### 터치와 입력

- 주요 터치 영역은 최소 44×44px로 만든다.
- 인접한 작은 버튼은 오작동하지 않을 간격을 둔다.
- 스와이프, drag, hover에만 존재하는 기능을 만들지 않는다.
- 세로 스와이프에는 항상 `다음 프로젝트` 버튼을 제공한다.

### 색과 대비

- 일반 텍스트는 최소 `4.5:1`, 큰 텍스트는 `3:1` 대비를 만족한다.
- 아이콘, 입력 경계, 포커스 표시 같은 필수 UI는 인접 색과 `3:1` 이상 대비를 목표로 한다.
- 상태와 선택을 색만으로 구분하지 않는다.
- 프로젝트 이미지 위 텍스트는 검증된 불투명 배경 또는 overlay 위에 둔다.

### 확대와 반응형

- 200% 텍스트 확대와 400% 화면 확대에서도 핵심 과업을 수행할 수 있어야 한다.
- 작은 화면에서 PDF와 폼 때문에 전체 페이지 가로 스크롤이 생기지 않게 한다.
- 브라우저 글자 크기를 고정하거나 확대를 막지 않는다.
- 고정 하단 CTA가 입력, 오류, 브라우저 UI를 가리지 않게 한다.

## 3. 구조와 이름

- 페이지마다 고유하고 구체적인 `title`과 하나의 주요 `h1`을 둔다.
- heading level을 시각 크기 때문에 건너뛰지 않는다.
- landmark와 semantic HTML을 우선하고 ARIA는 필요한 경우에만 추가한다.
- 아이콘 버튼은 `aria-label` 또는 화면 내 텍스트 이름을 가진다.
- 링크는 목적지를, 버튼은 행동을 설명한다.
- 현재 하단 탭에는 `aria-current="page"`를 제공한다.
- 동적으로 바뀐 중요한 상태는 적절한 live region으로 알린다.

## 4. 기능별 기준

### 피드와 스카우트

- 프로젝트 카드 전체 링크와 내부 저장 버튼의 포커스·클릭 영역을 분리한다.
- 프로젝트 이미지의 대체 텍스트는 제목과 중복되지 않게 목적을 설명한다.
- 영상 여부, 저장 상태, 스카우트 상태를 아이콘만으로 전달하지 않는다.
- 새 카드로 전환될 때 화면 낭독 사용자가 제목 변화를 알 수 있게 한다.
- 사용자의 명시적 동작 전 영상과 카드를 자동 재생·전환하지 않는다.

### PDF 상세

- 각 페이지 이미지에 `프로젝트 제목, PDF N페이지` 형식의 접근 가능한 이름을 제공한다.
- 페이지 번호와 전체 페이지 수를 텍스트로 알 수 있게 한다.
- lazy loading 중인 페이지가 읽기 순서나 포커스를 바꾸지 않게 한다.
- OCR 기반 대체 텍스트는 MVP 범위 밖이므로 PDF 자체의 시각 정보가 접근 가능하다고 주장하지 않는다.
- 원본 PDF 다운로드 제공 여부는 저작권·개인정보 정책과 함께 후속 결정한다.

### 업로드와 폼

- drag-and-drop 영역은 표준 파일 선택 버튼과 동일한 기능을 제공한다.
- 파일 유형·용량·페이지 제한을 선택 전에 안내한다.
- 진행률은 시각적 bar와 텍스트 값으로 제공한다.
- 오류 summary와 필드별 오류를 연결하고 첫 오류로 안전하게 이동할 수 있게 한다.
- 처리 중 화면을 나가도 되는지, 상태를 어디서 확인하는지 알린다.

### 제안

- 수락·거절·취소 버튼의 결과를 이름만으로 구분할 수 있게 한다.
- 되돌릴 수 없는 상태 변경은 실행 전에 결과를 설명한다.
- 근거 포트폴리오와 필요한 역할을 heading 또는 description 관계로 제안 문맥에 연결한다.
- 색이나 위치만으로 받은 제안과 보낸 제안을 구분하지 않는다.

### 채팅

- 새 메시지가 도착해도 사용자의 현재 읽기 위치를 강제로 이동하지 않는다.
- 본인이 화면 끝을 보고 있을 때만 새 메시지로 자연스럽게 이동한다.
- 메시지 작성자, 내용, 시각을 읽기 가능한 순서로 제공한다.
- 이미지 메시지는 발신자가 짧은 설명을 추가할 수 있는 방안을 후속 검토한다.
- 읽지 않음 수는 시각 badge와 접근 가능한 이름에 함께 반영한다.

### 매너와 통계

- 매너 상태는 색과 온도 숫자만으로 표현하지 않는다.
- 평가 선택의 이름은 `좋았어요`, `아쉬웠어요`로 읽히게 한다.
- 표본 부족 상태를 숫자 0과 구분해 설명한다.
- 통계가 사람의 실력이나 가치 점수가 아님을 정보 구조와 문구에서 유지한다.

## 5. 모션과 미디어

- `prefers-reduced-motion`을 존중한다.
- 깜빡임이 초당 3회를 넘는 콘텐츠를 사용하지 않는다.
- 장식 모션은 정보 전달에 필수적이지 않게 만든다.
- 영상은 자동 재생하지 않고 재생 전 음소거 상태로 둔다.
- 의미 있는 영상에는 자막 또는 동등한 텍스트 설명 정책을 후속 정의한다.

## 6. 테스트 기준

### 자동 검사

- axe 기반 핵심 페이지 검사
- Lighthouse Accessibility 점검
- TypeScript와 컴포넌트 테스트에서 accessible name 확인
- 색상 토큰의 대비 회귀 검사

### 수동 검사

- 키보드만으로 로그인 이후 각 핵심 흐름 완료
- Windows NVDA + Chrome 또는 Edge
- macOS/iOS VoiceOver + Safari
- 200% 텍스트 확대, 400% zoom, 320px viewport
- reduced motion, high contrast/forced colors 환경

### 핵심 시나리오

1. 피드에서 프로젝트 상세와 작성자 프로필 열기
2. 역할을 선택하고 버튼만으로 프로젝트 5개 탐색하기
3. PDF 업로드 후 처리 상태 확인하기
4. 제안을 읽고 수락·거절 중 하나 수행하기
5. 채팅 메시지를 보내고 읽지 않음 상태 확인하기
6. 매너 평가를 제출하고 완료 상태 확인하기

## 7. 완료 체크리스트

- [ ] 키보드만으로 핵심 과업을 완료했다.
- [ ] 의미 있는 모든 컨트롤에 accessible name이 있다.
- [ ] focus order와 화면 순서가 일치한다.
- [ ] 텍스트·UI 대비 기준을 만족한다.
- [ ] 색·모션·제스처의 대체 수단이 있다.
- [ ] 로딩·오류·완료 상태가 스크린 리더에 전달된다.
- [ ] 확대 시 콘텐츠와 CTA가 겹치지 않는다.
- [ ] 자동 검사와 최소 1개 스크린 리더 수동 검사를 통과했다.
